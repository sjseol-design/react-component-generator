# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸지 않는다.

## 적용 기준

### TDD를 반드시 적용하는 대상

- **비즈니스 로직**
- **API** (엔드포인트, 요청/응답 처리)
- **유틸 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD가 불필요한 대상

- **타입 정의**
- **설정 파일**
- **순수 UI** (로직 없는 마크업/스타일)
- **SQL**

경계가 모호하면 로직(분기, 계산, 변환)이 있는지로 판단한다. 로직이 있으면 적용한다.

## RED-GREEN-REFACTOR 사이클

### RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 오타, import 오류, 문법 오류로 인한 실패는 테스트를 고쳐서 올바른 이유로 실패시킨다.

### GREEN: 최소한의 코드로 통과

- 테스트를 통과시키는 **최소한의 코드만** 작성한다. **YAGNI** — 아직 테스트가 요구하지 않는 기능은 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는 것을 실행해서 확인한다.

### REFACTOR: 구조 개선

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지**한다. 변경마다 테스트를 실행한다.
- **새 동작 추가 금지.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

**테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.**

- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 해당한다.
- 삭제 후에는 테스트에서 요구하는 동작만 새로 구현한다.

## 변명 차단표

| 변명 | 반론 |
| --- | --- |
| "너무 단순해서 테스트 불필요" | 단순한 코드도 깨진다. 테스트는 30초면 쓴다. 단순할수록 비용이 더 싸다. |
| "나중에 테스트 추가하겠다" | 나중은 오지 않는다. 사후 테스트는 구현에 맞춰 쓰게 되어 버그를 잡지 못한다. |
| "시간이 없다" | 테스트 없이 만든 버그를 디버깅하는 시간이 더 든다. TDD가 더 빠른 길이다. |
| "삭제하면 낭비다" | 매몰 비용 오류다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. |
| "프로토타입이다" | 프로토타입은 프로덕션으로 간다. 버릴 코드라면 어차피 삭제 비용이 없다. |

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙을 우선**한다.
- **이 파일은 기본값(fallback)** 이다. 프로젝트 규칙이 없는 항목에만 적용한다.
